# ADR-002: Saved profiles with a partitioned library

**Status:** ACCEPTED — ratified by Finn 2026-09-14. Promote the terms below into `SPEC.md` (D2, FR-4, FR-5, FR-7, FR-8, FR-9, §6, §7).
**Date:** 2026-09-14
**Deciders:** Finn (maintainer)

## Context

D2 defines one versioned beat-profile: an NL brief, keywords, and few-shot
exemplars. The code loads one profile from `profiles/default.json` or the
`RICESEARCHER_BEAT_PROFILE` env var. Every scored slice records only
`beat_profile_version`. The library has no profile dimension.

Finn wants several saved profiles. A profile is a named content type with its
own scoring prompt. Media scored under one profile must not appear in another
profile's clip selection. The review UI must list profiles with counts and let
the user switch between them.

Three facts in the code shape the decision:

- `pipeline._slice_id` derives the slice id from source id and window only.
  Two profiles on one source would collide.
- `Library.replace_candidate_slices` deletes every candidate row of a source
  before a re-score. Two profiles on one source would wipe each other.
- The handoff manifest is a superset schema. RiceClipper keeps the whole clip
  object, so an added field costs it nothing.

## Decision

A **profile** is a JSON file in a profiles directory. Its id is the file stem.
Its version is a string in the file. Slices, dedup, review, and handoff are
**partitioned by `profile_id`**. Sources are shared. The user names the
profile on every scoring run.

### Q1 — Identity → id + version, slices pinned

- `profile_id` is the file stem: `^[a-z0-9][a-z0-9-]{0,39}$`. Stable for life.
- `version` is a free string. Finn bumps it when the prompt changes.
- A slice stores `profile_id` and `beat_profile_version`. An edit never
  rescores by itself. The UI marks a slice **stale** when its version differs
  from the file. A re-score replaces candidate rows under that profile only.
- Slice id becomes `{source_id}:{profile_id}:{in_ms}-{out_ms}`.

### Q2 — Partition unit → the slice row, keyed by profile

Sources and transcripts are shared. One source may be scored under any number
of profiles, one explicit run each. Dedup runs inside one profile only.
A profile's source count is the count of distinct sources with a slice under
it. Nothing is assigned by hand.

### Q3 — Prompt ownership → the profile file

Brief, keywords, and exemplars live in the file. The prefilter reads
`keywords` per profile, as today. Prefilter weights stay global. The scorer
prompt template stays in `anthropic_scorer.py`.

### Q4 — Handoff → `profile_id` per clip, schema stays 1

Each manifest clip gains `profile_id`. A batch holds one profile by
construction. RiceClipper needs no change. RicePoster never sees it.

### Q5 — Migration → adopt, no rescore

Schema v3 stamps every existing row with `example-beat` and rewrites `id`
and `dup_of` to the new id form. No API spend. Human-touched rows keep state.

### Q6 — UI → switch, list, counts

A profile select in the review topbar. A Profiles page with one row per
profile: name, version, sources, candidates, selected. Nothing else.

## Options considered

| Q | Chosen | Rejected | Why |
|---|--------|----------|-----|
| Q1 | file stem id + manual version | content-hash version | Hash churn on whitespace; Finn wants explicit bumps |
| Q2 | shared sources, explicit run | exclusive source per profile | Re-pull per beat wastes cache and time |
| Q2 | shared sources, explicit run | hand-attached membership | Extra clicks; count semantics unclear |
| Q3 | JSON file per profile | SQLite `profiles` table | Files diff and edit in a text editor (D2 rationale) |
| Q5 | adopt, no rescore | rescore all | Haiku spend for no new information |
| Q6 | select + list page | in-UI editor | Out of scope until asked |

## Consequences

**Easier**
- One library serves several beats. Cached media is reused across profiles.
- Handoff batches are profile-homogeneous. Clipper job titles can show it.

**Harder / to revisit**
- Every scoring, dedup, and handoff command needs `--profile`. No default.
- Migration rewrites primary keys. A v2 fixture DB must prove the upgrade.
- Cross-profile dedup is not computed. The same moment may be selected under
  two profiles. Advisory dedup across profiles is a later Issue.

## Routed forward

- Per-profile prefilter weights. Only if a profile's shortlist is poor.
- Profile create and edit in the UI.
- Cross-profile advisory dedup.
